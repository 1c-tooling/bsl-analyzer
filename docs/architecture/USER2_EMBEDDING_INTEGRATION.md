# Интеграция USER2-1C-code в BSL Analyzer

Дата исследования: 2026-09-30. Статус: проект интеграции, реализация и runtime-проверки не выполнялись.
Предполагаемая область: семантический поиск по коду рабочей конфигурации через существующий `search_code`.
Выбор новой модели по умолчанию остаётся результатом сравнительного испытания.

## Вывод

Подключить `PruhaNLP/USER2-1C-code` как дополнительный профиль существующего HTTP-эмбеддера.
Сначала воспроизвести профиль автора на 768 измерениях, затем проверить вариант без префикса документа и 256 измерений.
Первый кандидат для serving — готовый Text Embeddings Inference (TEI), после проверки совпадения с SentenceTransformers.
Не добавлять inference в Rust, новый vector store, reranker или автоматический выбор модели по длине вопроса.

## Что подтверждено источниками

- USER2 — специализированный bi-encoder на ModernBERT, контекст до 8192 токенов, выход 768d, mean pooling и cosine similarity.
- В конфигурации префиксы раскрываются в `search_query: ` и `search_document: `. `default_prompt_name` отсутствует как активное значение; pooling включает токены префикса.
- Автор заявляет обучение Matryoshka и практически одинаковый средний nDCG@10 для 768d и 256d: 0.599 и 0.598. Это основание для испытания, а не измерение на нашем корпусе.
- Опубликованный результат USER2: nDCG@10 0.4617 на `forum`, 0.7366 на `fastcode`. Qwen в опубликованной таблице модели отсутствует.
- `1C-Ebench`: 2883 пары `forum`, 530 пар `fastcode`, один эталонный документ на вопрос. Это поиск среди фрагментов ответов, а не среди методов полной конфигурации.
- Код `1C-RB` использует оба префикса, нормированные векторы и точный поиск. Среднее двух срезов — macro-average: каждому срезу присваивается одинаковый вес.
- Для Qwen документируется инструкция на вопросе и отсутствие инструкции на документе. Формат: `Instruct: <task>\nQuery:<question>`.
- TEI документирует ModernBERT, OpenAI-compatible endpoint, mean pooling, фиксацию revision и served model name. Совместимость конкретного checkpoint пока не проверена запуском.

Наблюдения из сообщения о Qwen 4B/8B, Q8 и скорости 5–6× остаются внешним экспериментом: картинка, параметры оборудования и сырые результаты не предоставлены. Нельзя переносить их на этот проект как подтверждённые показатели.
Срезы `forum` и `fastcode` различаются также источником и содержанием; их нельзя трактовать как чистый эксперимент над длиной вопроса.
Описание обучения не доказывает отсутствие пересечения обучающих данных с тестовыми: для независимой оценки нужен отдельный набор вопросов по нашим конфигурациям.

## Существующий путь поиска

```text
Документы: code_chunk → semantic_text_for_indexed_document → Embedder → SQLite/PG → vector index
Вопрос:    search_code → SearchEngine → Embedder → semantic candidates → fuse_smart → результат
```

Подтверждено чтением кода:

| Компонент | Текущий механизм | Следствие для интеграции |
|---|---|---|
| `crates/bsl-search/src/embedder.rs` | POST `<base_url>/v1/embeddings`, batch, dimensions, контроль ответа и размера | Переиспользовать транспорт; URL задавать без `/v1` |
| `crates/bsl-search/src/document.rs` | Единый текст: Module/Kind/Symbol, graph context, исходник | Сохранить формат; не ставить модельный префикс в общий документ или lexical index |
| `crates/bsl-search/src/engine.rs` | Отдельные query-вызовы `embed`, document batch и interactive overlay batch | Развести подготовку входа в общем эмбеддере, покрыв все способы вызова |
| `crates/bsl-search/src/ports.rs`, `publish.rs` | Общий `EmbeddingGenerator` для публикации документов | Сохранить документную семантику batch API |
| `crates/bsl-search/src/index.rs`, `hybrid.rs` | Cosine и `fuse_smart` с приоритетом точных идентификаторов | Сохранить текущую стратегию; не подменять её RRF |
| `store.rs`, `vector_persist.rs` | Cache и sidecar используют модель/размерность; есть версия текста | Добавить идентичность preprocessing в существующие проверки |
| `external_baseline/postgres.rs` | Модель и размерность закрепляются за PostgreSQL-схемой | Новый профиль испытывать в отдельной схеме; новый snapshot внутри старой схемы не решает несовместимость |
| `crates/mcp-server/src/broker/name.rs` | Fingerprint окружения включает URL/model/dim/provider | Учесть настройки префиксов, чтобы клиент не переиспользовал daemon другого профиля |
| `crates/mcp-server/src/state/bootstrap.rs` | Настройки через `EMBEDDING_*`, размерность по умолчанию 1024 | Для USER2 явно задавать 768 или проверенные 256 |
| `crates/bsl-analyzer/src/bin/cli/search_baseline/postgres.rs` | Своя сборка конфига из проекта и окружения | Publish и runtime должны разрешать одинаковый профиль |

## Предлагаемая архитектура

### Serving

Запускать один локальный TEI с закреплёнными model revision, версией/ digest контейнера и dtype.
Использовать полный tokenizer checkpoint, включая дополнительные токены; не заменять его tokenizer базовой модели.
Не включать серверный default prompt: префиксы добавляет клиент ровно один раз.
Сначала проверить полный выход 768d. Для 256d проверить поддержку `dimensions` именно выбранным serving runtime, усечение первых координат и последующую L2-нормализацию.
Если TEI не воспроизводит checkpoint или нужную размерность, использовать минимальный HTTP-адаптер SentenceTransformers с тем же API; не писать его заранее.

Локальный endpoint слушает loopback. Ввод кода и вопросы не писать в журналы сервиса. Общий удалённый endpoint требует отдельного решения о передаче кода.
Согласовать byte limit клиента с payload limit сервера, число элементов партии и серверный бюджет токенов. Byte limit не заменяет token limit.
Начать измерения с одной клиентской batch-задачи; увеличение concurrency определять по throughput и p95 интерактивного поиска при индексации.

### Префиксы

Добавить в `EmbedderConfig` два литеральных поля: `query_prefix` и `document_prefix`; для существующих конфигураций они пусты.
Вопрос добавляет только `query_prefix`, document batch и interactive overlay batch — только `document_prefix`.
Не проверять `starts_with`: текст пользователя может сам начинаться такой строкой. Роль задаёт вызывающий метод.
`embed()` сегодня вызывает interactive batch; после изменения он должен выбирать query-подготовку явно, иначе получит document prefix.
Планировщик партий должен учитывать байты итогового JSON с document prefix, а guard — ту же сериализацию.
Исходный вопрос остаётся входом lexical-поиска, определения формы запроса и `fuse_smart`.

| Профиль испытания | Вопрос | Документ | Размерность |
|---|---|---|---|
| USER2, воспроизведение автора | `search_query: ` | `search_document: ` | 768 |
| USER2, эксперимент из сообщения | `search_query: ` | пусто | 768 |
| USER2, компактный | выигравшая схема префиксов | выигравшая схема префиксов | 256 |
| Qwen, контроль | `Instruct: Given a 1C developer question, retrieve the matching 1C code fragment (BSL, query language, or module) that answers it.\nQuery:` | пусто | Явная размерность выбранного checkpoint |

`search_query` — имя prompt в USER2; для Qwen оно не является специальным токеном и не заменяет его собственную инструкцию.
Профиль Qwen Q8 фиксирует конкретный GGUF, serving runtime, pooling и revision; обозначения «4B Q8» для воспроизведения недостаточно.

### Идентичность векторов

Разделить HTTP model name и storage identity, не меняя схему хранения:

```text
HTTP model = immutable served alias закреплённого checkpoint/runtime-профиля
storage identity = alias + hash(query_prefix, document_prefix, preprocessing_version)
cache key = существующий semantic key + storage identity + dimension
```

Alias связывает веса, tokenizer, pooling, precision и политику обработки длинного ввода. Он не должен оставаться прежним при замене этих параметров.
Для профиля без новых настроек сохранить legacy identity, чтобы изменение не переиндексировало существующие установки.
Новая identity проходит через `EmbeddingGenerator::model_id`, overlay cache, publish, baseline comparison, freshness и vector sidecar. На HTTP отправлять исходный alias.
Статус должен различать served model и storage identity; совместимость проверять по второй.
Консервативно учитывать оба префикса в identity: изменение инструкции требует нового профиля и индекса, даже если векторы документов математически можно переиспользовать.
Авторизацию, URL и tuning batch/concurrency не включать в математическую identity; URL остаётся частью существующего broker fingerprint.

Для локальной SQLite недостаточно отвергнуть sidecar и собрать HNSW заново из старых BLOB: при несовпадении identity нельзя обслуживать старые векторы новым query-эмбеддером. Проверить provenance основной таблицы; для первого испытания использовать отдельный cache/индекс.
Baseline и overlay одного поискового представления должны иметь одинаковую identity и размерность.
Векторы Qwen и USER2 несовместимы даже при совпадающей размерности.

### Длинные фрагменты и области поиска

Начальный профиль не должен молча обрезать вход длиннее лимита tokenizer. Проверять длину с учётом префикса и заголовков; возвращать понятный отказ, сохраняющий lexical-доступ.
Во время испытания измерить долю таких фрагментов. Если она существенна, отдельно спроектировать разбиение длинных методов с сохранением ссылки на исходный символ и строки; не вводить это одновременно с заменой эмбеддера.
Сохранить graph context. Отдельный A/B на локальных вопросах проверяет raw code против существующего enriched text: модель обучалась на фрагментах, влияние заголовков пока неизвестно.
Справка платформы не покрывается code-retrieval бенчмарком. Первый пилот — workspace/code; reference-профиль сохраняет собственный эмбеддер в отдельном runtime. Один индекс не переключает модель по collection.

## План реализации и проверки

1. Воспроизвести USER2 768d по закреплённым версиям `1C-RB` и данных. Сохранить настройки, метрики по каждому срезу, per-query ranks, время и длины после tokenizer.
2. Сравнить TEI с SentenceTransformers на одинаковых коротких/длинных русских вопросах, BSL, SDBL и служебных токенах. Проверить близость векторов и top-k с учётом dtype, pooling и padding; измерить допуск до принятия runtime.
3. Реализовать query/document prefix и storage identity в общем клиенте. Согласовать конфиг MCP и CLI publish, broker fingerprint и передачу окружения daemon. Добавить соответствующие необязательные настройки проекта там, где уже описан embedding config.
4. Добавить проверки реального JSON для query, background batch и interactive overlay: точный префикс один раз, UTF-8 и граница byte limit. Проверить порядок ответа, размерность, конечность и ненулевую норму векторов.
5. Проверить смену profile: прежний cache/sidecar не обслуживается, baseline mismatch не публикуется, overlay и baseline не смешиваются. Старый профиль с пустыми префиксами работает как прежде.
6. Сравнить оба варианта USER2 768d, затем выигравший на 256d с локальным Qwen 4B Q8 и его инструкцией. Для Qwen отдельно показать текущую конфигурацию и конфигурацию с инструкцией, чтобы не приписать эффект prompt самой модели.
7. Проверить вопросы по реальной конфигурации: точные имена методов, описания поведения, вопросы с ошибочным кодом, запросы, клиент/сервер, extension/основная конфигурация. Разметить релевантные методы независимо от бенчмарка; при нескольких ответах учитывать их все.
8. Измерить semantic-only и конечный `search_code` с теми же chunking/graph context/fusion: nDCG@10, Recall@10, MRR@10, p50/p95, throughput индексации, RAM/VRAM, размер индекса, cold start и p95 под фоновой индексацией. Длину анализировать по токенам внутри каждого среза, а не только по названию источника.

Для выбора 256d сравнить per-query изменения и bootstrap-интервалы с 768d; при спорном качестве оставить 768d.
Для миллиона float32-векторов 768d занимает 3.072 GB, 256d — 1.024 GB только полезных координат. Это не оценка общей памяти HNSW или размера SQLite/PG.
Нормализация после усечения обязательна для сопоставления dot-product и cosine в проверках.

Принятие интеграции требует live-вызова `search_code` по контрольным вопросам, изменения файла и повторного поиска через overlay, холодного запуска с сохранённым индексом и проверки отказа сервиса с доступным lexical-поиском.
Unit-тесты и OpenSpec validation не заменяют эту проверку. Численные пороги качества и задержки выбрать по baseline до переключения используемого профиля.

## Переход и откат

Пилот строится в отдельном локальном индексе и, если используется central baseline, отдельной PostgreSQL-схеме.
Полностью рассчитать и проверить документы новым профилем, затем переключить consumer и согласованный overlay. Публикация новой схемы и переключение рабочих сервисов — отдельная реализация, не часть этого исследования.
Сохранить прежние Qwen-профиль, схему и cache для отката. Не удалять их автоматически.
В первый этап не входят одновременные индексы USER2/Qwen в одном runtime, маршрутизация по длине, reranker, ONNX и квантование USER2.
Добавлять их только после обнаруженной на измерениях потребности.
